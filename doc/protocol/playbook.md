# Driver playbook: Plustek's engine mapped onto pyopticfilm

Plustek's own driver, read as the playbook for the OpticFilm 120 (`../work/0012-driver-playbook.md`). Each section takes one topic, derives the requests from the macOS engine's code first, checks them against the issue #151 capture second, and maps them onto pyopticfilm's GL128 code third, so that the OpticFilm 120 lands in pyopticfilm as a model configuration rather than as a replay tool. Each section ends with the pyopticfilm change it implies. Topics, in the order of the work item: standby, open, and moves and homing (below), then scan. The sections "Status and flags", "Resets" and "Self tests" are the inventory of the engine's debugging facilities for `../work/0013-debugging-facilities.md`, and "Requests the firmware handles" lists what the owner's unit has and has not been sent.

Conventions:

- Addresses are offsets in the x86_64 slice of the macOS `ScanApi` 1.4.27.4.0 (`../vendor-driver/macos.md`). Decompiled functions are cited by file name and line. The files are in `work/re/decomp-x86_64/`, the disassembly in `work/re/disasm-x86_64/` (untracked, made as described in `../../tools/ghidra/README.md`).
- The Windows V5.0.2.0 engine is cited as `FUN_<address>` by file and line in `work/re-win/decomp-x64/` (untracked, `../vendor-driver/windows.md`, "Disassembly"). The reconstructed engine source in `engine/` (private submodule, `../work/0014-decompiled-code-cleanup.md`) is cited by function name and address only.
- Scripts named in a section (`blast_vs_plist.py` and the like) were throwaway checks run with `python3 -I` outside the repository. What each compared is stated where it is used, so that it can be redone.
- "The plist" is `ScanInfoVID_07B3_PID_1406.plist` of the macOS package (`../vendor-driver/macos.md`, "Layout"), cited by line. It is the only configuration the engine loads for the OpticFilm 120 (`../vendor-driver/macos.md`, "Which configuration file").
- Capture frames are those of `of120-capture-151.md` (decoded listing in `work/captures/151/annotated.txt`).
- pyopticfilm is cited at submodule commit `32dc576` (release 1.3.5), paths relative to `pyopticfilm/src/pyopticfilm/`.
- The OpticFilm 120 runs the engine's `CGL126` class, field positions from `gl128-registers.md`. Data registers and output enables pair up as `0x31`/`0x34` (GPIO1 to 8, GPOE1 to 8), `0x32`/`0x35` (9 to 16), `0x33`/`0x36` (17 to 24) and `0x37`/`0x38` (25 to 32). ## Standby

In short: the engine's only standby line is GPIO8 (`0x31` bit 7, plist `StandbyReg`). At open the register blast sets it high together with its output enable (`0x34` bit 7), then `Register` pulls it low for 10 ms and high again. While the engine runs, a 5 s tick reads `0x31` and sets bit 7 again only when it finds it clear. At close the engine clears it. No other GPIO and no other register is treated as a host-present or wake signal. On the owner's unit, GPIO8 driven high without the pulse did not hold the unit, the full open with the pulse did, so the smallest write set to try is those same two writes plus the engine's pulse. pyopticfilm has no standby handling, which matches the engine for the 8200i SE (its configuration has no `StandbyReg`). An OpticFilm 120 model needs an open hook and a close hook.

### 1. GPIO writes at open

**How the engine writes GPIO registers.** There are three ways, and this model uses two of them.

- Register shadow and blast. `CRegistry::ReadSettings(-1,-1,-1,-1)` (`0x08c260`) calls `CRegistry::ReadKey(NULL)` (`0x08b090`). That clears the register shadow and the property array (`CRegistry__ReadKey@0008b090.c` lines 66 to 68), copies the base blob `0` into the shadow and marks each register for the next blast with `CRegister::SetLink` (lines 122 to 137), then applies every key that names a register. A key `rr.mm` sets the bits of mask `mm`: `(old & (mm ^ 0xffff)) + value` (lines 238 to 245). A key `rr` alone overwrites from register `rr` on (lines 247 to 254). Named keys such as `StandbyReg` go into the property array through the name table `m_prop` (lines 197 to 220), so a key the plist lacks reads 0 (the clear at line 68, and in `CRegistry__CRegistry@00089dc0.c` line 35). `CIOUSB::WriteAllReg` (`0x0f3650`) sends every marked register in marking order and clears the marks (`CIOUSB__WriteAllReg@000f3650.c` lines 34 to 40).
- Selectors keyed by the plist: they read a register, change the bits a key names and write it back (`CAsic::LoaderEjectSel`, `CAsic::StandbyModeSel` and the others in the table below).
- Named field setters (`_GPIO8`, `_GPOE8`, ...), which change the shadow and either write the register or mark it (`CGL126__GPIO8@00075c20.c` lines 15 to 21). None writes a GPIO register on this model's open path. The only ones in the call tree are `_GPIO22` and `_GPIO23`, behind plist key `CPLDDpiSet`, which the plist lacks (`CScanApi__SoftwareResetScanner@000338a0.c` lines 53 to 57), and `_GPOADF`, a stub that returns 1 in `CGL126` (`CGL126__GPOADF@0004f7f0.c`). The interrupt thread started at open reads `0x37` once through the getter `_GPIO25(…, 1)` (`CScan__WaitInterruptEvent@000e3ef0.c` line 91, `CGL126__GPIO25@000ebb80.c` lines 13 to 17), a read only.

### 2. The engine's standby model

- Line and polarity. `StandbyModeSel(true)` clears the `StandbyReg` mask in `0x31`, `StandbyModeSel(false)` sets it, and both do nothing when `StandbyReg` is 0 (`CAsic__StandbyModeSel@00061ac0.c` line 24). `CAsic::IsStandbyMode` (`0x061d60`) reads `0x31` and reports standby while the bit is clear (`CAsic__IsStandbyMode@00061d60.c` lines 28 to 32 and 45 to 50). `CScanApi::StandbyModeControl` (`0x038e50`) wraps it: `true` sets the engine's flag `this[0x1b8]`, `false` clears it and sets `_g_fSkipStandbyOffTimer` (`CScanApi__StandbyModeControl@00038e50.c` lines 8 to 17).
- Timer. `CScanApi::InitStandbyModelOffTimeInfo` (`0x022ee0`, called at the end of `SoftwareResetScanner`) needs `StandbyReg` (line 17), reads `StandbyOffTime` (15, plist lines 59 to 60), sets the limit to `(StandbyOffTime - 5) * 60000` ms with `StandbyOffTime` raised to at least 5, the step to 5000 ms, and starts the timer (`CScanApi__InitStandbyModelOffTimeInfo@00022ee0.c` lines 23 to 31). `CNotify::SetStandbyModeTimer` (`0x0889c0`) creates a run loop timer with interval `0x4014000000000000`, 5.0 s. `Timer` (`0x088ab0`) calls the notify callback with `0xff`, and `CScanApi::EventHandler` (`0x038600`) runs `TestUnitReady`, then `SetStandbyOffTime` (`CScanApi__EventHandler@00038600.c` lines 16 to 19).
- Each tick, `CScanApi::SetStandbyOffTime` (`0x0387a0`) works only while no scan runs and `_g_fSkipStandbyOffTimer` is clear (`CScanApi__SetStandbyOffTime@000387a0.c` line 23), and only when `TestUnitReady` returns ready (line 25). Then:
  - `LoaderReadyReg = 0x31,0x04` (plist lines 152 to 153): `CAsic::IsLoaderReady` (`0x06b020`) reads `0x31` and reports ready unless bit 2 (GPIO3) reads set twice (`CAsic__IsLoaderReady@0006b020.c` lines 24 to 39). A ready holder ends the tick: the engine sets bit 7 if `IsStandbyMode` finds it clear and resets the idle count (lines 29 to 39).
  - `LoaderSensorReg` would do the same with the holder's home sensor (lines 43 to 55). The plist has no such key.
  - Before the limit, if the engine's flag is set or `IsStandbyMode` finds bit 7 clear, `StandbyModeControl(false)` sets it and resets the count (lines 78 to 86).
  - The count grows by 5000 (line 90). At the limit the engine calls `StandbyModeControl(true)` and logs `"SetStandbyOffTime : scanner set into standby mode in 5 min !\n"` (lines 91 to 95), and it clears the bit again whenever it later finds it set (lines 97 to 106).
  - While a scan runs, or on the first tick after any `StandbyModeControl(false)`, the tick only resets the count and clears the skip flag (lines 129 to 132). So every `StandbyModeControl(false)` restarts the 10 minute idle count.
  - Per tick with this plist, the engine therefore sends reads of `0x31` and, only when bit 7 is clear or at the limit, one read-modify-write of `0x31` bit 7. It writes no other register and sends no pulse.
- `CScanApi::TestUnitReady` (`0x0232f0`) sends nothing on the tick path. It reads and clears `CNotify::m_Notice` (`CScanApi__TestUnitReady@000232f0.c` lines 30 and 31) and acts on bits `0x21`, `0x12` and `4` (lines 32, 62 and 96). The decompiled code has three writers of `m_Notice`: `DeviceAttach` (`0x0886a0`) ORs in `0x10`, `DeviceDetach` (`0x088710`) `0x20`, `Timer` `0x3000` (`DeviceAttach@000886a0.c` line 13, `DeviceDetach@00088710.c` line 15, `Timer@00088ab0.c` line 10). The tick's `0x3000` matches none of the three tests. After a USB attach (`0x10`) it runs `Unregister` and the whole `Register` again (lines 62 to 95), so the engine meets a unit that has re-enumerated with a new open, pulse included. Its `StandbyModeControl(false)` (line 51) needs bit 0 of `m_Notice`, which none of the three writers sets, so on macOS it does not run *(inference: a writer that Ghidra did not decompile would change this)*. `../vendor-driver/macos.md`, "Standby", lists `TestUnitReady` among the callers without that condition.
- The interrupt thread `CScan::WaitInterruptEvent` (`0x0e3ef0`, started by `CScan::OpenInterruptDetect` at `Register` line 83) computes a `StandbyReg` flag (lines 102 and 103) and never uses it. With this plist (`PollingButtonEvent = 1`, plist lines 393 to 394, skips the button branch at line 374; no `CoverSel`, no `LoaderInterruptReg`), its only register traffic is the holder eject check: while a holder is positioned, sleep 500 ms, then `IsLoaderReady` (lines 290 to 307), and 50 ms per loop (line 472).
- Other callers, from a search of the decompiled and disassembled files for `StandbyModeSel`, `StandbyModeControl` and `IsStandbyMode`: `StartScan` (`0x027c50`, `CScanApi__StartScan@00027c50.c` lines 254 and 478), `DoCalibration` (`0x034120`, line 25), `ExeDoCalibrate` (`0x046a80`, line 161) and `CAddOn::StartStaticScan` (`0x0030e0`, line 572) set the bit. `Unregister` (`0x01f470`) clears it (`CScanApi__Unregister@0001f470.c` lines 87, 190 and 195). No caller writes any other register as part of standby. The Windows engine has the same design (`../vendor-driver/windows.md`, "Question 5: standby").

So the engine knows one line, GPIO8, and one host-side event besides its own timer that re-asserts it: a ready film holder on GPIO3. A unit that leaves and rejoins the bus gets the full `Register`.

The capture agrees:

- Frames 127 to 138: the pulse at open.
- Frames 13473 to 13478 (278.65 s): read `0x31` → `0xbb`, write `0xbb`, a `StandbyModeControl(false)` with the bit already set, before the second preview *(inference: paired by shape, the capture is of the Windows engine)*.
- Frames 15479 to 15532 (301.9 s to 318.0 s): 27 reads of `0x31`, 0.61 s to 0.63 s apart (submit times in `work/captures/151/transfers.jsonl`), and no write. That fits the eject check's 500 ms plus the loop's 50 ms, with the holder ready (`0xbb`, bit 2 clear, one read per check) *(inference)*.
- Frames 15537 to 15542 (read `0xbb`, write `0x3b`) and 15873 to 15878 (read `0x3b`, write `0x3b`): the close clears bit 7.
- No other write to `0x31` occurs apart from the 12 blasts, which all write `0xfc`.

During the replayed pulse the unit read `0x31 = 0x3c` (frame 133 record of the same log), bit 7 low, so the pulse reached the pin.

Reading of these facts *(inference throughout this paragraph)*: GPIO8 reads high while its output is disabled (`0x31 = 0xbc` with `0x34 = 0x00` before any write), so the line idles high with no host, and a high level alone cannot tell the board's microcontroller (U11, `../hardware/board.md`) that a host is there. What the engine adds on this line is its low periods. The log line "scanner set into standby mode in 5 min", written right after the engine clears the bit, and the host limit of `StandbyOffTime` minus 5 minutes point to a 5 minute countdown in the unit, which is the 4 min 55 s seen after every wake. One model fits all four runs: the unit's countdown runs from a wake and from a falling edge of GPIO8, and a rising edge after a low period stops it. `keep_awake.py` never made the line low, `vendor_open.py` held it low for 13 ms. The open did not merely restart a 5 minute countdown either, since the unit stayed 7 minutes past the pulse.

The first run that holds names the group, and the search continues by halves inside it: for B, `0x37`/`0x38` with `0x30` and `0x39` against `0x32`/`0x35` and `0x33`/`0x36`, for C the clocks with `0x114`/`0x115` against the blast. What an OpticFilm 120 model entry needs:

- GPIO values: `init_regs` with the GPIO area of part 1 (blob `0` plus patches, equal to frame 21).
- A standby hook in the open path after the blast: `LoaderEjectSel` (set `0x36` bit 1, then `0x33` bit 1), then the GPIO8 pulse (clear bit 7 by read-modify-write, 10 ms, set bit 7). `Gl128._update_bits` (`asic/gl128.py` lines 247 to 253) is the read-modify-write it needs. The model carries the line as data, `(0x31, 0x80)` from `StandbyReg`, and the existing models carry none, so the hook does nothing for them. If run A does not hold, the hook grows by the group the search finds.
- A close hook that clears `0x31` bit 7, as `Unregister` does, so that the unit falls back to its own standby.
- While open, setting bit 7 again when it reads clear, before each operation or on a timer, as `SetStandbyOffTime`, `StartScan` and `DoCalibration` do. Releasing the line after 10 idle minutes (`StandbyOffTime`) is host policy and optional *(inference)*.
- A caution for the later steps: pyopticfilm writes `0x33` as a depth register (`REG_DEPTH_A`, `asic/registers.py` line 90, written at `asic/gl128.py` lines 487 and 820) and `0x37` bit 2 as the infrared LED (`REG_IR`, `asic/registers.py` line 91, `asic/gl128.py` lines 1287 to 1292). On the OpticFilm 120 both are GPIO data registers with other keys on them. `0x33` carries `LoaderEjectSwitch` (GPIO18, plist lines 146 to 147), `MotorReg = 0x33,0x20,0x00` (GPIO22, lines 167 to 168), `SOLReg = 0x33,0x00,0x40` and the `33.40` patches of `Positive`, `Negative`, `PositiveIR` and `NegativeIR` (GPIO23, lines 603 to 604, 179, 292, 399, 506), `IRMask = 0x33,0x80,0x80` (GPIO24, lines 128 to 129) and `33.10` in `SPEED1` and `SPEED2` (GPIO21, lines 621 and 674). So the SE's `0x33` writes must not carry over to this model *(inference: the key names give the use)*.

pyopticfilm change this section implies: a standby line field on the GL128 model (unset for the 8200i SE, 8100 V2 and 8300i SE), an open hook after the blast that sends the eject-switch bits and the pulse when the field is set, a close hook that clears the bit, and a re-assert of the bit before operations. Nothing changes for the existing models. The hook's content waits for run A, so that it carries what the unit needs.

## Open

In short: the engine's open is the plist's register image plus a short list of values that code derives from other plist keys, and nothing in it moves the motor. The capture's blast (frames 17 to 36) is that image byte for byte and in the engine's order, so no blast value is computed. The computed values are the two clock bytes, the DRAM refresh value, the lamp-off write, the AFE defaults, and the read-modify-writes of the eject switch and the GPIO8 pulse. The Windows engine V5.0.2.0 sends one block on the first open in a process, and that block matches frames 15 to 138. The macOS engine sends the same block with a `SoftwareResetScanner` before it and a second block after it, which repeat values already set and add one write, `0x0e = 0x00`. `vendor_open.py` is the Windows first open, so the owner's unit has had the engine's open. pyopticfilm's `asic_boot` and `init` differ from it in the points of part 4, which the OpticFilm 120 entry has to carry.

## Moves and homing

In short: four engine functions produce every carrier move of the capture, and their arithmetic with the plist's values gives the capture's `FMOVNO` and FEEDL for all five moves whose distance is fixed. FEEDL does not count the ramps: a move is FEEDL steps plus `FMOVNO` steps up and `FMOVNO` steps down, as the engine's arithmetic and the capture's timing both indicate (part 3). `0x33` bit 5 is the engine's drive select (`MotorReg`, `CAsic::MotorSel`): with it set the engine scales distances with the second entry of `MotorDPI`, 310 steps per inch against 5333, and it sets it for the film loader moves (move 2, move 3, the reverse and the exit move). The home sensor changes only in moves with the bit clear. The engine homes in two ways and neither is a move with `MTRREV`: `AGOHOME` after each image brings the carrier back onto the home sensor, and `HolderHomeCarriage` runs the loader drive with BACKSCAN toward the slot. The open homes nothing. So the owner's two moves, replays of move 3, ran on the drive whose moves never change the home sensor in the capture, and the test of the drive with the home sensor was move 1 (`move_carrier.py --as-move-1`). That test ran on 2026-10-15 11:40 UTC and the carrier moved: `HOMESNR` cleared 0.135 s after the start write, the feed finished at 0.45 s, and the owner heard it (`../hardware/probes/20261015T114043Z-move-carrier-move-1.jsonl`, `../work/0011-first-motor-move.md`).

### 1. The engine's move functions

- `CAsic::Unit2Step` (`0x054b80`): steps = distance in units × (`MotorDPI[i]` shifted left by `FSTPSEL`) / `UnitDPI`, with `UnitDPI = 10600` (plist lines 745 and 746), `MotorDPI = 5333,310` (lines 165 and 166) and `FSTPSEL` from `0xa0` bits 5 to 3. `i` is 1 while the engine's flag `0x25c` is set (with `MotorSel` for a film source, and by `HolderHomeCarriage`) or its ADF flag `0x24c`, otherwise 0. A unit is 1/10600 inch.
- `CAsic::MoveCarriage(distance, …)` (`0x0545d0`): saves `ACDCDIS`, FEEDL, `LPERIOD`, `TGTIME`, `TBTIME` and the exposure times, clears `ACDCDIS`, `NOTHOME` and `AGOHOME`, sets `MTRPWR` and `FASTFED`, and sets `MTRREV` for a negative distance. For bcdDevice `0x606` and up: `FMOVNO = min(steps / 2, MotorStep - 1)` and `FEEDL = steps - 2 * FMOVNO`. Then `WriteAllReg` (call `0x054a61`), `WriteFastTable` (`0x054a7f`) and `_MOVE` (`0x054aa6`, `0x0f = 0x01`). It puts the saved values back into the shadow only, so the next `WriteAllReg` sends them. `MotorStep` is 256 (`CAsic::CAsic`, `0x0521a0`), the plist has no `MotorSteps`.
- `CAsic::MoveWithDetectSensor(value, distance, wait)` (`0x05ca90`): `FMOVNO = min(steps / 4, MotorStep / 2 - 1)`, `FEEDL = steps - 4 * FMOVNO`, start, then a loop that reads `MOTORENB` (call `0x05cf05`) and the event byte (`CIOUSB::Interrupt`, call `0x05cf50`, wIndex `0x21` for this product, "Status and flags", part 2). `wait` is the pause in µs after a failed event read. When the byte equals `value`: `MTRPWR` off (`0x02 = 0x08`) and FEEDL 1, `WaitMotorStop(1500)`, `MTRPWR` on (`0x02 = 0x18`), then the saved values back into the shadow. `value` is the second number of `MoveDetectSensor = 1,64,100` (plist lines 169 and 170) or `LoaderDetectSensor = 1,32,240` (lines 144 and 145), the third the distance in percent of `UnitDPI` (`usb-requests.md`, "Interrupt and buttons").
- `CAsic::HolderHomeCarriage` (`0x06b3a0`): `WaitMotorStop`, `MotorSel(3)` (call `0x06b401`), distance `FilmLoaderOrigin` (`0,980`, lines 96 and 97) × `UnitDPI` / 1000, doubled because `LoaderDetectSensor` is set and `Enable35mmFilmLoader = 0` (lines 88 and 89), less a length the caller passes (applied because `FilmLoaderSize` is set, lines 98 and 99). Then flags `0x25f` and `0x25c`, `_BACKSCAN(1)` (call `0x06b631`), `FMOVNO = min(steps / 4, 127)`, `FEEDL = steps - 2 * FMOVNO`, `WriteAllReg`, `WriteFastTable`, `_MOVE`, `WaitMotorStop`, `_BACKSCAN(0)` (`0x06bc1c`) and `MotorSel(0)` (`0x06bc45`). Its eject variant first asks `IsLoaderOnHomeSensor`, which reports true without `LoaderSensorReg` ("Status and flags", part 1).
- `CAsic::MotorSel(source)` (`0x05d5f0`) with `MotorReg = 0x33,0x20,0x00` (lines 167 and 168): reads `0x33` (call `0x05d670`). For a film source (1 positive, 2 negative, or 3) it writes `MTRPWR` on (`0x02`) and `ADFSEL` off (`0x0a = 0x48`) and sets bit 5. For source 0 it writes the same two and clears bit 5. For the ADF sources (4, or `-1`) it sets bit 5 and takes `STEPSEL` and `FSTPSEL` from `AdfStepSel`. Then it writes `0x33`. That is the capture's pattern at every change of bit 5: read `0x33`, write `0x02`, `0x0a`, `0x33` (`of120-moves.md`, "What the capture does not show").
- `CAsic::WriteFastTable` (`0x055b80`): builds the table with `CAsic::GetMotorTable` (`0x056fc0`) from the plist's `Motor` curves (lines 154 to 164: `Curve 30,3000,180`, `DetectSensorCurve 110,800,240`, `LoaderSensorCurve 110,240,440`), `MotorBackRatio = 100` (lines 51 and 52), `FSTPSEL` and `MotorStep` entries, and writes it to `0x1000c000` and `0x10010000` (`CGL126::MotorAddr`, `0x080e40`). Which curve each move uses was not traced, and the tables were not recomputed.
- `CAsic::HomeCarriage` (`0x056bb0`): when `HOMESNR` is clear and `MOTMFLG` reads clear twice, `MoveCarriage` by `HomeCarriageStep` (`0,-6`, lines 124 and 125, six inches back, so with `MTRREV`) and `WaitMotorStop(1500)`. `WaitMotorStop` (`0x056d80`) reads `MOTORENB` every 1 ms while `TickCount` has advanced less than its argument, and `_TickCount` is an imported stub of Carbon's `TickCount` (the engine links Carbon, `work/re/strings-x86_64.txt`), which counts sixtieths of a second, so 1500 is up to 25 s, about the time a six-inch move takes at move 1's speed. Neither function asks the ASIC for a stop at the sensor, so whether a reverse move ends at `HOMESNR` by itself (`NOTHOME` clear) is not known from the engine. `tools/pi/move_carrier.py --home` replays this shape on the owner's unit as move 1 with `MTRREV` set, and stops the move itself when `HOMESNR` sets. Its first run (2026-10-15 13:20 UTC, `../hardware/probes/20261015T132025Z-move-carrier-home.jsonl`) brought the carrier back onto the sensor from 754 steps out in 0.69 s, so `MTRREV` reverses the carrier drive on this unit (`../work/0011-first-motor-move.md`). ### 3. FEEDL and the ramps

Two sources agree that FEEDL leaves the ramps out:

- The engine: `MoveCarriage` and `HolderHomeCarriage` set `FEEDL = steps - 2 * FMOVNO` for a move of `steps`, which is a move of `FEEDL + 2 * FMOVNO` steps if the ASIC adds `FMOVNO` steps at each end *(inference: the intent read from the arithmetic)*.
- The timing. `ramp_timing.py` takes `tables/slope-6353.hex`, which move 3 (`FMOVNO` 255, FEEDL 97) and the exit move (127, 961) share, and the times from the start write to the first `FEEDFSH` and to `MOTORENB` clearing (`of120-moves.md`, "Overview"). Model A: the ASIC steps through `FMOVNO` table entries up, FEEDL steps at the last entry, sets `FEEDFSH`, steps through `FMOVNO` entries down and clears `MOTORENB`. It needs one time unit per table count: 0.244 to 0.250 µs from move 3's `FEEDFSH`, 0.248 to 0.250 µs from the exit's, and 0.251 to 0.267 µs and 0.249 to 0.273 µs from the two ramps down. One unit of about 0.25 µs fits all four within 1 %. Model B, `FEEDFSH` only after the whole move, needs 0.133 to 0.137 µs for move 3 and 0.208 to 0.210 µs for the exit, which do not agree. FEEDL counting the ramps cannot hold for move 3, where FEEDL 97 is less than 2 × 255.

So a move is `FEEDL + 2 * FMOVNO` steps, and its time is the sum of the table entries up and down plus FEEDL times the last entry used *(inference: one step per table entry, as in SANE's GL124 backend)*. That answers the first point of `of120-moves.md`, "What the capture does not show", for the moves that run to their end. Move 3 is 607 steps, 0.98 inch at 620 steps per inch (`MotorDPI[1]` with `FSTPSEL` 1).

### 4. `0x33` bit 5

- Engine: `MotorSel` sets the bit for every source except 0 (part 1). `StartMove` and `HolderHomeCarriage` call it with the film source around exactly the moves that `Unit2Step` scales with `MotorDPI[1]` (flag `0x25c`), and with 0 after them. So the bit and the 310 steps per inch go together: the bit selects a second drive path, with a scale 17 times coarser than the first. Whether that path is a second motor, a second gear train or a second driver channel, the engine does not say. The board has a quad 2-input multiplexer with no known role (U5, CD74ACT157M, `../hardware/board.md`, "Parts"), which a select line of this kind would fit *(inference, no physical step proposed)*.
- Capture: the bit is set for moves 2 and 3, the reverse and the exit move, clear for moves 1 and 4, and no other write changes it (`of120-moves.md`, "What the capture does not show"). `between.py` replays every register write from frame 139 to 6256 (from after the open to move 1): no write in that range sets it. `HOMESNR` changes only while the bit is clear: move 1 leaves the sensor and the `AGOHOME` park after the image returns to it. In the four moves with the bit set it keeps its value, clear in moves 2 and 3, set in the two BACKSCAN moves (`of120-moves.md`, "Direction"). That fits a second drive that moves something the home sensor does not watch *(inference)*. It is an alternative to the reading in `of120-moves.md`, "Direction", that the BACKSCAN moves keep the sensor covered beyond home.
- Owner's unit: `move_carrier.py` replays move 3, so both of the owner's moves ran with the bit set, starting at home (`../work/0011-first-motor-move.md`). A constant `HOMESNR` is what the capture shows for every such move, so the home sensor says nothing about motion in those runs. Only the owner's report that nothing was heard or seen does. Move 1 is the capture's one move with the bit clear that starts on the home sensor, and `HOMESNR` clears during it. `move_carrier.py --as-move-1` replays it (`../work/0011-first-motor-move.md`), and its first run (2026-10-15 11:40 UTC, 97 steps) moved the carrier: `HOMESNR` clear from 0.135 s after the start, `MOTORENB` clear at 0.45 s, `0x101 = 0xf0` afterwards, motion heard by the owner. So the carrier drive, its driver and the home sensor work on the owner's unit, and the two silent runs were the drive that bit 5 selects, with nothing in the slot for it to move *(inference: whether that drive turned silently or not at all is not known; the holder test in `../work/0013-debugging-facilities.md` is its check)*.

## Status and flags

In short: the engine learns the unit's state from the two status registers `0x101` and `0x100`, from the GPIO data registers, from a few one-byte vendor reads and from an event byte that arrives either on the interrupt endpoint or through a polled read. Its API status calls read at most `0x101`, `0x100` and `0x31`. The button status, the unit-ready test and the last error read nothing from the unit. The engine has a full register dump, `CScan::DumpAllRegFromAsic`, which reads `0x01` to `0x120` one register at a time, but it runs only at debug level 4 and up, and the OpticFilm 120's settings leave the level at 0. Apart from the home sensor and the event byte, no flag the engine reads reports anything downstream of the motor outputs. A snapshot made only of IN requests that the engine or the capture uses is in part 3.

### 2. The flags, and who reads them

**`0x101`.** Bits and the capture's values are in `of120-moves.md`, "Status values". ## Resets

In short: two resets give a state a tool can verify by reading back. A standby and wake cycle (the power button) gives the cold state, the same register values on the wakes of 2026-10-13 and 2026-10-15. `CScanApi::SoftwareResetScanner`, which the engine runs at open, around scans and calibrations, and as `apiReset`, gives the state the plist defines: the blast, clocks and DRAM refresh. `SCANRESET` on its own writes `0x0e = 0x00` and has no effect anyone has seen. `CIOUSB::HardwareResetScanner` sends `40 xx 008b` wIndex 4 with one byte `00` and has no caller in any engine build read so far. A USB port reset is not used by the engine for this model. The effect of these last two is unknown.

### 1. What each reset sends

**`SCANRESET`.** `_SCANRESET(false, 1)` writes `0x0e = 0x00` (`CGL126__SCANRESET@0004f270.c` lines 16 and 21 to 23). The engine never writes 1 there. SANE's GL124 cold start writes `0x0e = 1`, then 0 (`backend/genesys/gl124.cpp` lines 1246 to 1249), and so does pyopticfilm's GL845 `soft_reset` (`asic/gl845.py` lines 74 to 76, used when `is_cold_boot`, lines 84 and 85). The capture has no write to `0x0e`. Writing 0 alone releases a reset nobody asserted *(inference)*.

**`CScanApi::SoftwareResetScanner`** (`0x0338a0`). In order (`CScanApi__SoftwareResetScanner@000338a0.c`):

1. read `0x03` for the lamp state, `_LAMPPWR(…, 1)` and `_XPASEL(…, 1)` (lines 26 and 27). The `SevenSegment` keys are absent, so lines 28 to 38 send nothing.
2. `_SCANRESET(false, 1)`, `0x0e = 0x00` (line 40).
3. `ReadSettings` (line 41), the lamp bits put back into the shadow (lines 47 to 52), so the reset keeps the lamp as it was. `CPLDDpiSet` is absent (lines 53 to 57).
4. the full blast `WriteAllReg` (line 58): blob `0` with the patches, the same bytes as frame 21. It includes `0x02 = 0x78` (`MTRPWR`, `AGOHOME`, `../hardware/usb.md`, "Standby"), `0x06 = 0x18`, `0x31 = 0xfc` and `0x34 = 0x80`.
5. system and AHB clock, `ENBDRAM` off, `RFHSET`, `ENBDRAM` on (lines 83 to 96). `MotorReg` has no fourth value, so no phase table (lines 97 to 102). `FlashRAM = 1` (plist lines 102 and 103): `SPI_init` and `SFlash_RDID` (lines 103 to 108). 100 ms sleep (line 110). The lamp-off time (lines 111 to 116) does not apply to `LampType 1`.
6. `_ADFSEL`, `_GPOADF` and a second `WriteAllReg` of what was marked since (lines 117 to 119), `WriteAllAfe` (line 120).
7. `InitStandbyModelOffTimeInfo` (line 128): the host's 5 s timer, no GPIO8 pulse. The pulse is in `Register` ("Standby", part 1, row 10).
8. only if the host believes a holder is in position and no error is pending: `WaitMotorStop` and `CAsic::HolderHomeCarriage` (`0x06b3a0`), a carrier move (lines 129 to 152). The belief is host state (`CScan__IsFilmHolderPosition@0008df10.c`, `_g_dbFilmLoaderLastMovingLength`), so in a fresh process the function returns at lines 133 and 134 without moving.

`apiReset` (`0x033820`) calls it and returns 0 on success (`apiReset@00033820.c` lines 14 to 21). The engine also runs it in `Register` (line 69), `StartScan` (`CScanApi__StartScan@00027c50.c` lines 186, 225, 291, 355 and 584), at ten points of `StopScan`, in `EndScan` (line 75), `ExeDoCalibrate`, `DoCalibration` and `Oldapi`. The capture's 12 blasts fit that *(inference: the capture is of the Windows engine)*, but it has no `0x0e` write, and pyopticfilm's GL128 `asic_boot` says the Windows driver never writes `0x0E` (`asic/gl128.py` line 1249).

**`CIOUSB::HardwareResetScanner`** (`0x0f8370`): under the USB lock, `ControlWrite(this, 0x8b, 1, &zero, 4)` (`CIOUSB__HardwareResetScanner@000f8370.c` lines 15 to 17). `ControlWrite`'s arguments are (wValue, wLength, buffer, wIndex) (`usb-requests.md`, "Common rules", `CIOUSB__ControlWrite@000f0eb0.c` lines 32 to 37), so the request is `40 xx 008b` wIndex 4, one byte `00`, as `usb-requests.md`, "Reset, self tests", and `serial-flash.md`, "wIndex values", already have it (the work item's "wIndex 1, four zero bytes" does not match the call). No caller: no decompiled function references it, and its address appears in the x86_64 slice only in the symbol table. The Windows V5.0.2.0 equivalent `FUN_1801039e0` sends the same request (`FUN_1800fd300(param_1, 0x8b, 1, local_18, 4)`) and is referenced only from `.pdata` (`0x180132170`), the V6.0.0.0 one (`FUN_18016ecb0`) only from `.pdata` (`0x1801e99cc`), with no stored pointer to either in its DLL. wIndex 4 sits among the command numbers of the `0x8a`/`0x8b` port (3 AHB address, 5 and 6 APB, 7 and 9 `SPI_init`, `0x0b` to `0x12` flash). What the unit resets on it (registers, the USB core, the whole chip) is not known.

**USB port reset.** The macOS engine re-enumerates only `07b3:131c` on close (`CIOUSB__ClosePipes@000f13e0.c` lines 16 to 22, `serial-flash.md`, "Where the USB identity comes from", item 6). pyopticfilm resets the device only after an aborted bulk stream (`usb/device.py` lines 407 to 415, flag set at line 558). When the unit does re-enumerate, the engine meets it with a full `Register` ("Standby", part 2).

**Standby and wake, power cycle.** The owner's unit leaves the bus about 5 minutes after a wake unless it is opened (`../hardware/usb.md`, "Standby"). The 24 V power cycle runs a motor move of the firmware's own (`../hardware/usb.md`, "Power"). Whether a wake from standby does too is not recorded.

pyopticfilm change this section implies: none.

**What this suggests for the motor.** Nothing the engine reads sits downstream of the ASIC's motor outputs. The only feedback from the mechanics is the home sensor (`0x101` bit 3) and the event byte, whose `0x40` and `0x20` end the vendor's moves 1 and 2 when a sensor trips (`usb-requests.md`, "Interrupt and buttons", an inference there for the sensors). `MOTORENB`, `FEEDFSH`, `MOTMFLG` and `HISPDFLG` describe the ASIC's own step sequencer *(inference: the engine never checks them against a sensor)*. On the owner's unit the sequencer behaved like the working unit's in both moves (above), so the ASIC side of the move ran. Reading `0x100` together with `0x101` during the next move adds one check: if `MOTMFLG` and then `HISPDFLG` come up as in the capture's parks, the ASIC believes it is stepping, and the fault sits between its motor pins and the motor (driver, its supply or enable, cable, motor) *(inference)*. If they stay clear while `MOTORENB` is set, the sequencer is in a state the working unit never showed. The capture reads `0x100` only during AGOHOME parks, not during a FEEDL move, so the comparison is between different kinds of move. `0x06` bit 4 and `0x101` bit 7 still set after the move would rule out the ASIC losing its set-up during it, as a supply dip would cause *(inference)*. The owner's logs show bit 7 set after both moves. The snapshot also reads back the motor-related outputs, `0x02` and GPIO22 (`0x33` bit 5, `MotorReg = 0x33,0x20,0x00`, plist lines 167 and 168, used by `CAsic::MotorSel`, `0x05d5f0`), for comparison with the vendor's move 1, the one capture move with proven motion (`../work/0011-first-motor-move.md`). No read tells a driver that gets no steps from one that gets steps and cannot turn the motor. That takes a measurement at the motor driver on the board, a physical step for the owner to weigh (`../hardware/board.md`, "Reassembly").
