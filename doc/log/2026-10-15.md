The owner reassembled the unit after the board photos. The EEPROM read and keep-awake write no motor register, so they go ahead as planned, each with the owner's go-ahead.

## EEPROM read over USB does not reach the chip #eeprom #diagnosis

With the owner's go-ahead, `tools/pi/eeprom_read.py` ran once on a fresh power-up (2026-10-14 22:08 UTC, `doc/hardware/eeprom-read.md`): every word `0000`, and the data registers held `00` before the first command. That is the result the exposure-register reading predicted, so the USB route to U19 is closed by the rule in `doc/protocol/serial-eeprom.md`. Next: a read in circuit with an SOIC-8 clip on the Pi's GPIO, which is a hardware purchase and the owner's decision.

## Keep-awake enabled #standby

`keep-awake-enabled` now exists on the Pi, so the watcher runs `tools/pi/keep_awake.py` on every wake. Whether the unit then stays on the bus past five minutes is checked on the next wake. The flag has to go before any further `eeprom_read.py` run.

## Driving GPIO8 does not keep the unit awake #standby

On the next wake (22:16:55 UTC) the watcher drove GPIO8 high with its output enable set, and the unit still left the bus 4 min 55 s later (`doc/hardware/usb.md`, "Standby"). The five-minute timer is not held by that line alone. Keep-awake is disabled again; the button stays the way to wake the unit until a full initialisation can be tried, which waits for the mechanical check.

## The vendor open sequence keeps the unit awake #standby #usb

With the owner's go-ahead, `tools/pi/vendor_open.py` ran once on the wake of 06:14:33 UTC. The unit was still on the bus 7 min 20 s later, where every earlier wake ended at 4 min 55 s (`doc/hardware/usb.md`, "Standby"). The home sensor bit was set before the open, as before the opening of the unit, so the gate let the sequence through. Decision: the open sequence becomes the first thing sent on every wake once the owner agrees to that standing run, since it also leaves the motor powered and holding (`0x02 = 0x78`, as the vendor does). Until then each run keeps needing a go-ahead. Which part of the sequence holds the unit, and for how long, is measured on the following wakes.

## The vendor engine is the playbook #method #driver #pyopticfilm

Owner's direction after the open-sequence result: the official drivers are to be read as playbooks. The engine's standby code already says how the vendor keeps the unit awake (`doc/vendor-driver/macos.md`, "Standby"), so the open holding the unit is no surprise, and the question is only what in `Register` makes the line effective. Decision: every sequence sent to the unit is derived from the engine's code first, confirmed against the capture second, and mapped onto pyopticfilm's GL128 code third (`doc/work/0012-driver-playbook.md`). The capture stays the check that a derived sequence is what the working unit received.

## Decompiled vendor code stays out of the repository #method #driver #licensing

Both engines are decompiled in full (macOS `ScanApi` x86_64 slice, 2710 functions; Windows `Scanapi_x64.dll` V5.0.2.0 and V6.0.0.0, 2184 functions, plus the WIA clients), in `work/re/` and `work/re-win/`. Owner's decision: hold the checking in of that output. The repository is public under AGPL and the output is derived from Plustek's binaries. The Ghidra scripts and the exact commands (`tools/ghidra/README.md`) regenerate it, and the documents cite function names and addresses.

## First host-driven move: the engine ran, the motor did not #hardware #motor #mechanics

With the owner's go-ahead and at the unit, `tools/pi/move_carrier.py` sent the vendor's 97-step move 3 after the open (`doc/hardware/probes/20261015T072134Z-move-carrier.jsonl`). Every write was acknowledged and the status bits changed with the working unit's timing (feed finished at 0.585 s, motor idle at 1.080 s, against 0.585 s and 1.086 s in the capture), but the owner heard and saw nothing, and the home sensor bit stayed set. The register state matched the capture's at the start write except the lamp, and the engine's `CAsic::MoveCarriage` (`0x0545d0`) sends nothing beyond what the capture shows, so the gap is below the ASIC: motor driver power or enable on the board, or the firmware's own control of it. The configuration has no motor power selector keys (`CAsic::MotorPowerSel`, `0x05e990`, and `MotorBusPowerSel`, `0x061860`, do nothing for this model) and `MotorReg = 0x33,0x20,0x00` names bit 5 of `0x33` as the motor source select (`CAsic::MotorSel`, `0x05d5f0`), which the move set as move 3 does. Next: the owner checks that the firmware's own power-on run still moves the motor, then the board photos and the engine decide what enables the driver.

## Debugging facilities before more moves #method #debugging

Owner's direction: inventory the unit's and the engine's debugging facilities (flags, status, self tests, resets) and find a reset that gives a known state, before more blind moves (`doc/work/0013-debugging-facilities.md`). First facts from the engine: the ASIC and flash self tests are stubs, the SDRAM test is a real write and read-back, the hardware reset is a single vendor request the engine never calls, and the soft reset is what `Register` does at open.

## The opening was not needed #hardware #retrospective

The owner opened the unit on my request for board photos. In hindsight the photos served only the identity-restoration path: the board revision had a read-only test already built, and a Linux user-space driver, the owner's stated preference, does not need the USB identity at all. The reassembly may have hurt the mechanics (`doc/work/0010-mechanical-check.md`). Rule from here on: no physical step without its value for the stated goal, the non-invasive alternatives and the risk written out first, as a decision for the owner.
