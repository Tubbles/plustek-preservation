# 2026-10-14

## The flash does not hold the identity #flash #diagnosis

With the owner's go-ahead, `tools/pi/flash_dump.py` read the whole serial flash (EON EN25F40, 512 KiB) in 35 s, two identical passes. It holds the infrared record at address 0 and nothing else (`doc/hardware/flash-dump.md`). That rules out the counter reset as the cause and the flash as the place the USB identity lives on this unit. Next candidate: a serial EEPROM on the ASIC's EEPROM interface, which Plustek's engine can read (`CAsic::ReadFromNVRAM`) but never does. Board photos and a read over USB are the next steps. The USB read means register writes beyond the SPI requests, so it needs its own review and the owner's approval.

## No firmware update path in either driver #windows #firmware #diagnosis

The owner suspected a botched automatic firmware update. Both engines rule that out as far as Plustek's own code goes: `apiUpgradeFirmware` is a stub on Windows (V5.0.2.0 and V6.0.0.0) as on macOS, no shipped Plustek client calls the counter reset, and neither engine writes a USB identity or an EEPROM (`doc/vendor-driver/windows.md`, "Disassembly"). What third-party applications (SilverFast, VueScan) call is still open.

## Keep-awake waits for the board revision #standby #hardware

`tools/pi/keep_awake.py` drives GPIO8 high as the vendor does, but on the newer OpticFilm 120 board (added to Plustek's driver on 2022-11-18) that pin is the film loader sensor. The owner bought the unit before 2022, so the original board is very likely. The watcher runs the tool only once `keep-awake-enabled` exists, which waits for a read-only check: insert and remove the film holder and see which bit of `0x31` follows.
