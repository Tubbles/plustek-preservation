# 0011 First motor move after the reassembly

Status: in progress

The owner wants to test the mechanics by moving the holder carrier (`0010-mechanical-check.md`). This item is the tool and the procedure for the first host-driven motor command, built so that each run is bounded and replays only what the working unit in the issue #151 capture received (`doc/protocol/of120-moves.md`, extracted and reviewed on 2026-10-15).

What the vendor does, as the capture shows:
- Every move comes after the open sequence (register blast, clock set-up, AFE defaults, GPIO set-up) and is preceded by a pair of identical 512-byte slope tables to `0x1000c000` and `0x10010000` (`doc/protocol/tables/`).
- A move is `0x02 = 0x18` (MTRPWR, FASTFED), FEEDL (`0x3d` to `0x3f`) in steps, `0x0f = 0x01` to start, then polling of `0x101` until MOTORENB (bit 0) clears. Moves 1 and 2 of each cycle wait on the interrupt endpoint instead and are cut short by an event (inference), after which the driver writes `0x02 = 0x08`. After moves 3 and 4 it leaves `0x02 = 0x58`, so motor power stays on.
- The shortest move that runs to its programmed length is move 3: 97 steps, table `slope-6353.hex`, `0x33` bit 5 set by read-modify-write before and cleared after. It starts with the carrier off the home sensor.
- The only direction bit the driver uses is BACKSCAN (`0x09` bit 3): set for the two moves toward the slot, both of which start on the home sensor. MTRREV is never set. Without BACKSCAN the carrier moves away from the home sensor, the direction that draws the holder in (inference).
- Position is counted from the home sensor (`HOMESNR`, `0x101` bit 3) and the holder sensor (`0x31` bit 2, `LoaderReadyReg`); the frame positions and `FilmLoaderOrigin 0,980` are constants in the driver configuration, and the flash holds only the infrared record. No stored position calibration was found anywhere, so a carrier moved by hand needs no recalibration (inference: as far as the engine and the flash show).

Steps:
- [x] Read-only first: at the next wake, log `0x101` (home sensor) and `0x31` (holder sensor) and compare with the values before the opening (`0x4c` and `0xbc`, `doc/hardware/usb.md`). The firmware moves the motor briefly at every power-on (owner, 2026-10-15), so the mechanism has already run since the reassembly; the owner thinks the carrier now sits near the middle of its travel. If `HOMESNR` is clear after a power-on, the power-on move is not a homing or the sensor no longer trips, and that has to be understood before any move. Result (wake of 2026-10-15 06:14 UTC, `doc/hardware/probes/20261015T061444Z-vendor-open.jsonl`): `0x101 = 0x4c` and `0x31 = 0xbc`, the same as before the opening. `HOMESNR` is set, so either the carrier sits on the sensor or the sensor reads set for another reason; the first move away from home has to show the bit clearing, which the move tool logs.
- [x] Extract from the capture the exact bytes of the moves: `doc/protocol/of120-moves.md` and `doc/protocol/tables/`, reviewed against the raw capture (2026-10-15).
- [x] Build `tools/pi/vendor_open.py`: the open sequence (capture frames 15 to 138) replayed verbatim, then a watch of the bus for the standby question. Unit tests, reviewed by a second agent (2026-10-15). It refuses to write unless the carrier is at home with the motor idle (`--carrier-off-home-ok` overrides). Its first run is also the standby experiment (`doc/hardware/usb.md`, "Standby") and gives the home sensor reading of step 1. Ran once on 2026-10-15 06:14 UTC: every write acknowledged, and the unit stayed on the bus past the five minutes.
- [x] Build the move tool on top of it: `tools/pi/move_carrier.py` (2026-10-15, reviewed by a second agent). Register state of move 3 rebuilt by a test from the capture, the lamp left off as the only difference, `0x33` reset to the vendor's value first, the 19-register block with a chosen FEEDL (default 97), the table pair, the start, polling every 15 ms with `HOMESNR` and `MOTORENB` logged until MOTORENB clears or a limit passes (then the vendor's cut of moves 1 and 2 before the clean-up), the vendor's writes after the move and `0x02 = 0x08` so that motor power is off at the end. Refuses any other write, and refuses to run unless the open has been sent since the wake. `--backscan` adds only the direction bit, which no vendor move does exactly.
- [x] Decide the direction with the owner from where the carrier sits now, then one run with the owner at the power switch and an explicit go-ahead. Listen for a stall. Done twice on 2026-10-15 (07:21 and 07:36 UTC, the second with the lamp register as captured): the step engine ran with the working unit's timing, the owner heard and saw nothing, the home sensor bit stayed set (`doc/log/2026-10-15.md`). The firmware's own power-on run does turn the motor (owner).
- [ ] `--as-move-1` is built (replays the vendor's move 1, the only capture move with proven motion from home: bit 5 of `0x33` clear, table `slope-6267`, the 27-pair block of frame 6259), 177 tests, review by a second agent pending, not deployed. Whether to run it comes after the debugging inventory (`0013-debugging-facilities.md`).
- [ ] If the short move runs clean: a homing run (`0x02 = 0x30`, AGOHOME, as in the park at the end of a pass) with a poll limit, which finds the sensor, then record the outcome in `doc/hardware/board.md` and close `0010`.

Risks, for the owner's decision: a move into an end stop or a mis-seated gear stalls the stepper. Whether a stall can damage the gear train in this unit is not known. The vendor's own moves 1 and 2 run until an event stops them and the firmware moves the carrier at every power-on, so the mechanism is built for ordinary stalls and unattended moves, but a mis-seated gear is not an ordinary case. The 97-step move is the shortest the vendor sends and uses the slowest of its tables.
