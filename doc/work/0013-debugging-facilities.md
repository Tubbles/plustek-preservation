# 0013 Debugging facilities: status, flags, self tests, resets

Status: todo

Owner's direction (2026-10-15, after two host-driven moves ran the step engine with the working unit's timing and moved nothing, `0011-first-motor-move.md`): before more blind moves, inventory what the unit and the engine offer for debugging. Flags to read out, status to query, built-in self tests, and whether a soft reset brings the unit into a known, deterministic state. Each facility is derived from the engine's code first (`0012-driver-playbook.md` method), checked against the capture where it appears, and classed as read-only, write without motion, or motion.

Known so far, from the decompiled macOS engine (`work/re/decomp-x86_64/`, untracked):
- `CIOUSB::AsicSelfTest` (`0x0f83e0`) returns 0 and `CIOUSB::FlashSelfTest` (`0x0f8410`) returns 1 without touching the device: stubs. `CIOUSB::SdramSelfTest` (`0x0f8430`) is a real test: it writes a fill byte to a memory range with `WriteData`, reads it back with `ReadData` and compares. No decompiled function calls any of the three, so the engine does not run self tests on its own.
- `CIOUSB::HardwareResetScanner` (`0x0f8370`) sends one control write, wValue `0x8b`, wIndex `4`, one zero byte, under the USB lock (`doc/protocol/usb-requests.md`; the decompiler's argument order misled an earlier reading of it as wIndex 1 with four bytes). No decompiled function calls it, and neither Windows engine has a caller for its counterpart. What the firmware does on it is not known.
- `CScanApi::SoftwareResetScanner` (`0x0338a0`) is what `Register` runs at open: `SCANRESET` (`0x0e = 0x00`), the settings read, the full register blast, clocks, DRAM refresh, flash ID (`doc/protocol/playbook.md`, "Standby", row 2). `apiReset` (`0x033820`) is its API entry.
- Status readers: `apiGetDeviceStatus` (`0x023180`), `CScanApi::GetModuleStatus` (`0x023a90`), `GetPaperStatus`, `GetLampStatus`, `GetButtonStatus`, `CScan::GetMyLastError` (`0x0401c0`), `CScan::DumpAllRegFromAsic` (`0x0bde50`) and `CIOUSB::DumpAllRegistersToConsole` (`0x0f8790`), `CIOUSB::ReadInterrupt` and `GetInterruptVal`, `ReadButtonID`. Register-level flags already known: `0x101` status bits (`doc/protocol/of120-moves.md`, "Status values"), `0x100` flags (`COVERSNR`, `CHKVER`, `DATAENB`, `MOTMFLG`, `HISPDFLG`), the GPIO data registers, `VALIDWORD` (`0x102` to `0x105`).
- Resets available in principle, from least to most invasive: `SCANRESET`; the `0x8b` wIndex `4` request; a USB port reset from the host (libusb `reset_device`, standard USB, effect on this firmware unknown); the 24 V power cycle, which is the firmware's own reset and runs its homing move (`doc/hardware/usb.md`, "Power").

Steps:
- [x] Status readers and dump functions (`doc/protocol/playbook.md`, "Status and flags", 2026-10-15): the API status calls read at most `0x101`, `0x100` and `0x31` (lamp is `0x101` bit 2, module status is `HOMESNR` plus `MOTMFLG` away from home, paper status is `0x31` bit 2); button status, `TestUnitReady` and `GetMyLastError` read nothing from the unit; `DumpAllRegFromAsic` reads `0x01` to `0x120` but only at debug level 4, which the plist sets to 0. The engine reads nothing downstream of the motor outputs except `HOMESNR` and the event byte. The section ends with the snapshot request list (IN requests only) for a read-only tool, which is the next deliverable.
- [x] Resets (`doc/protocol/playbook.md`, "Resets"): a standby and wake cycle gives the same cold values on both wakes on record and clears at least `0x34`; `SoftwareResetScanner` (`apiReset`) gives the plist-defined state, checkable against frame 21, but its blast powers the motor; `SCANRESET` alone writes `0x0e = 0x00` with no effect seen; the `0x8b` wIndex `4` request and a USB port reset are unknowns, to be classified by diffing snapshots.
- [x] Self tests (`doc/protocol/playbook.md`, "Self tests"): `SdramSelfTest` is the only real one, touches SDRAM only, and tells nothing about the motor; the Windows `FlashSelfTest` erases the flash and is never to be run.

Nothing in the capture reads those two registers.

What the engine cannot tell (playbook, "Self tests", closing paragraph): polling `0x100` during a move shows whether the ASIC believes it is stepping, but no read distinguishes "no steps reach the driver" from "driver or motor fault". That needs a measurement on the board. Host-side avenues still open, in order:
- Holder present. The working unit had the film holder inserted when it moved: `0x31` read `0xbb` before move 1 (bit 2, `LoaderReadyReg = 0x31,0x04`, plist line 152, clear, which `CAsic::IsLoaderReady`, `0x06b020`, reports as ready), `0xbe` right after the open at 18.2 s with no holder yet, while the owner's unit reads `0xbc` with the holder out. The engine itself does not gate a move on that bit: `IsLoaderReady` is called only from `CScanApi::GetPaperStatus` (`0x023b60`, the API status call), `CScanApi::SetStandbyOffTime` and the interrupt thread's eject detection (`CScan::WaitInterruptEvent`, `0x0e3ef0`, lines 290 to 307), never from `StartScan`, `SetScanParam`, `StartMove` or `CAsic::MoveCarriage`. The loader home sensor check `IsLoaderOnHomeSensor` (`0x06bc90`) reads `LoaderSensorReg`, which the plist lacks, so it always reports "on sensor". Whether the firmware enables the carrier drive only with a holder present is therefore not answerable from the engine; if it does, every move so far was bound to do nothing *(inference)*. Test: insert the empty holder with the unit on and connected, watch what the firmware does on its own (the Quick Guide says it ejects a holder once a computer is connected, `doc/research.md`), then one move with the holder in.
