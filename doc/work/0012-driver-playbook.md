# 0012 The vendor engine as the playbook, mapped onto pyopticfilm

Status: todo

Owner's direction (2026-10-15): read the official drivers as playbooks. The open sequence held the unit on the bus (`doc/hardware/usb.md`, "Standby"), and the engine's code says why it should: `StandbyModeSel` keeps bit 7 of `0x31` set and `Register` pulses it at open (`doc/vendor-driver/macos.md`, "Standby"). Setting the bit alone did not hold the owner's unit, so the open does something more that makes the line effective, and the engine's `Register` is where that is written down. From here on every sequence sent to the unit is derived from the engine first, confirmed against the issue #151 capture second, and mapped onto pyopticfilm third, so that the OpticFilm 120 support lands as a model configuration in pyopticfilm rather than as a replay tool.

Sources: the macOS engine keeps its symbols (`doc/vendor-driver/macos.md`, "Symbols"; Ghidra project per `tools/ghidra/README.md`), the Windows engine is the same code base (`doc/vendor-driver/windows.md`, "Disassembly"), the capture is decoded in `doc/protocol/of120-capture-151.md` and `of120-moves.md`, and pyopticfilm's GL128 code is `pyopticfilm/src/pyopticfilm/asic/gl128.py` (`asic_boot`, `init`, `feed`, `home`, `park`, `_upload_fast_slopes`, `wait_until_at_home`, `stop_motor`).

Steps, one topic at a time, each a section in `doc/protocol/playbook.md` with the engine function names and addresses, the capture frames that confirm the sequence, the pyopticfilm function that does the same job for the 8200i SE, and what differs:
- [x] Standby (`doc/protocol/playbook.md`, "Standby", 2026-10-15): the engine knows one line, GPIO8, set by the blast with its output enable, pulled low for 10 ms by `Register`, re-set by a 5 s tick when found clear, cleared at close. No other GPIO or register is a host-present signal. The GPIO bytes of the capture's blast are the plist's blob with its patches, byte for byte. Smallest write set to test on a later wake: the keep-awake writes plus the pulse, with a bisection order after it. pyopticfilm has no standby handling, which matches the engine for the SE models (no `StandbyReg`), so the OpticFilm 120 entry needs an open hook (eject-switch bits, pulse), a close hook and a re-assert before operations.
- [x] Open (`doc/protocol/playbook.md`, "Open", 2026-10-15): the capture's blast is the plist's root image byte for byte and in order (118 pairs, checked by script), so no blast value is computed. The computed values are the clock pair (`0x0d` from `SystemClock`), the DRAM refresh toggle, the lamp-off write, the AFE defaults from key `@`, and the read-modify-writes of the eject switch and the pulse. The Windows engine V5.0.2.0 sends exactly that block on a first open. The macOS engine wraps it in `SoftwareResetScanner` and a second block that add only `0x0e = 0x00`. Nothing in the open moves the motor. `vendor_open.py` is the Windows first open. pyopticfilm's `asic_boot` needs, for this model, the plist image as `init_regs`, no AHB blobs, memory layout, GPO block or table uploads at boot, and an open hook with the clock, DRAM, lamp, AFE, eject switch and pulse writes.
- [x] Moves and homing (`doc/protocol/playbook.md`, "Moves and homing", 2026-10-15): `StartMove`, `MoveWithDetectSensor`, `MoveCarriage` and `HolderHomeCarriage` with the plist's values reproduce `FMOVNO` and FEEDL of moves 1 to 3, the reverse and the exit move exactly. FEEDL leaves the ramps out: a move is `FEEDL + 2 * FMOVNO` steps (engine arithmetic and capture timing agree). `0x33` bit 5 is `MotorSel`'s drive select: set, the engine scales distances with `MotorDPI[1]` (310 per inch against 5333) and uses it for the loader moves, in which the home sensor never changes. Homing is `AGOHOME` after each image plus BACKSCAN loader moves, never `MTRREV`, and none at open. The owner's moves replayed move 3 on that second drive, so `--as-move-1` is the test of the drive with the home sensor. pyopticfilm needs `FMOVNO` computed per move, a drive select field and BACKSCAN as direction for this model.
